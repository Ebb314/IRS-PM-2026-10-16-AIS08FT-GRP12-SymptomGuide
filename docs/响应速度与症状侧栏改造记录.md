## 本次范围

保留 Qwen3-4B-Instruct-2507、本地 NF4 量化、自由文本语境理解、近 16 条对话上下文、15,135 个症状节点检索及证据校验。没有回到人工意图分类，也没有换成预设问答。队友的召回、Informed Search 接口继续保留；独立运行使用 random 适配器。

本次解决两件事：减少固定串行生成开销；让用户能看清、修改和确认症状记录。没有使用跨会话回答缓存，也没有把用户重复说的 yes 缓存成固定答案。

## 延迟改造

原流程每轮固定执行：LLM 理解 → 生成草稿 → LLM 重写草稿；理解输出损坏时另有 JSON 修复调用，回答重复时还可能重试。对于本机 GPU，这些都是串行生成。

新流程默认 `AGENT_REPLY_PIPELINE=direct`：

1. LLM 继续结合实际上下文输出自由文本目标、指代、歧义及症状建议。
2. 原证据校验继续决定是否允许写入；模型理解结果同时作为回复上下文。
3. 复用原来最终回复阶段的语境与约束，由 LLM 直接生成最终回复，跳过前面的草稿生成。额外强调不能冒充患者，空记录时没有症状下拉框，知识解释不应附带记症状操作。
4. 如果程序检测到空输出、完全重复、过长或旁白式输出，仍调用 LLM 修复；失败时保留明确失败提示。

初次实验曾直接返回原草稿，虽较快，但出现以患者身份编造描述的问题，因此弃用。失败输出保留在 `evaluation/performance-draft-rejected.json`，不作为交付版成果。`performance-pipelines.json` 中的 direct 行才是最终版本。

这是“条件触发修复”，不是独立模型审查的等价替代。程序不能识别所有语义错误。保留 `AGENT_REPLY_PIPELINE=reviewed` 可恢复固定草稿加重写模式，适合对比和回退；两者使用相同模型、检索与证据规则。自然语言回复质量仍取决于本地模型。

性能数据及逐条回答见 `evaluation/performance-pipelines.json`。测试脚本用内存数据库，在模型及索引加载完成后计时；计时包含服务调用内的检索、理解、回答、校验及存储，不包含 HTTP、模型冷启动。两组分别连续运行相同多轮用户输入，各自保留真实生成的历史，因此后续上下文内容可能不同。此为单机小样本，不代表生产 SLA。

另测了 PyTorch 8、1、4 个 CPU 线程，固定模型和 62 个生成 token 的回复，结果没有稳定改善，故未更改线程默认值。原始数据见 `evaluation/runtime-thread-benchmark.json`。没有将这项实验当成提速成果。

## 新侧栏：My symptoms

| 区域 | 意义 | 操作 |
| --- | --- | --- |
| Present | 用户报告当前存在；不是医学确诊 | Change status 改为 Absent / Not sure |
| Absent | 用户明确报告当前没有；不是临床排除诊断 | 可改回 Present / Not sure |
| Not sure | 已记录该概念，但当前状态不确定 | 确认后改为 Present / Absent |
| Confirm a suggested match | 模型提议的语义匹配，尚未写入症状记录 | 确认概念匹配后选择状态，或 Ignore suggestion |

每组显示数量；支持搜索已保存的症状。原始文字、轮次、KG ID、来源位于 Record details。保存成功以服务端返回的版本及分组为准；错误时不提前显示成新状态。请求处理中锁定编辑，避免基于过期版本并发修改。

“不确定症状状态”和“不确定语义匹配”是不同问题，因此分开展示。忽略一个匹配不会把症状记成 Absent，也不会清除已有记录。状态修改会进入历史记录并刷新召回 / 搜索适配器输入；Not sure 不加入阳性或阴性召回输入。

原来的模型追踪、候选疾病和药物关系折叠到单独区域，避免与个人症状混在一起。random 模式输出明确标为集成测试结果。人工修改状态后直接返回保存确认，不调用 LLM，也不突然弹出随机候选症状的 Yes / No 按钮。

## API 与实现位置

- `frontend/src/components/SymptomPanel.vue`：状态分组、计数、搜索、下拉编辑及匹配确认。
- `frontend/src/views/ChatView.vue`：侧栏整合、诊断信息折叠、等待计时。
- `frontend/src/stores/chat.ts`：复用原有版本控制及幂等请求机制。
- `backend/app/models/chat_models.py`：`CorrectionRequest.status` 新增操作值 `dismiss`；症状本身仍只有 present / absent / uncertain 三种状态。
- `backend/app/services/chatbot_service.py`：只允许修改已有记录或当前 pending 建议，拒绝任意 KG ID；忽略仅适用于 pending；agent 模式的明确修改直接保存并更新适配器。
- `backend/app/services/conversation_agent.py`：默认直接回复、条件修复、保留 reviewed 模式，更新侧栏操作说明。

继续调用 `POST /api/chat/correct`，提交 `session_id`、`expected_version`、`request_id`、`kg_id`、`status`。`dismiss` 不是第四种症状状态。已有记录不可用 dismiss 删除。过期版本及非法操作返回 409；失败后重试必须复用原 request_id。成功后刷新页面从 SQLite 恢复状态。

## 手动运行

不需要下载模型或安装额外依赖。使用此前的 gc1 环境和 Node 22：

```powershell
conda activate gc1
cd E:\Study\StudyAtNUS\GC1_Project\frontend
npm run build
cd ..
$env:AI_PROFILE='local'
$env:DIALOGUE_ENGINE='agent'
$env:AGENT_REPLY_PIPELINE='direct'
$env:LOCAL_MODEL_4BIT='true'
$env:LOCAL_MODEL_PATH='E:/Study/StudyAtNUS/GC1_Project/models/Qwen3-4B-Instruct-2507'
$env:EMBEDDING_MODEL_PATH='E:/Study/StudyAtNUS/GC1_Project/models/all-MiniLM-L6-v2'
$env:NLP_ENGINE='rules'
$env:NLP_USE_TRANSFORMERS='false'
$env:REASONING_MODE='random'
$env:HF_HUB_OFFLINE='1'
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --no-access-log
```

如端口已有本项目服务，应先停止原服务再启动，避免运行两份 GPU 模型。浏览器打开 `http://127.0.0.1:8000/`，刷新后确认右侧标题是 My symptoms。

复现对比时先停止 GPU 服务，再执行：

```powershell
python scripts/compare_reply_pipelines.py
```

脚本使用同一模型依次比较 reviewed 与 direct，各 13 轮；写入 `evaluation/performance-pipelines.json`，会覆盖该报告。它使用独立内存数据库，不修改用户已有会话。运行需要数分钟。
