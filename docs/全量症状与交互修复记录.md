# 全量症状接入与交互修复记录（2026-09-15）

## 1. 修改范围与数据核对

实际工程目录为 `E:\Study\StudyAtNUS\GC1_Project`。本机不存在消息中带额外反斜杠的 `GC1\_Project\...\kg\_nodes.csv`，本次使用工程现有的 `backend/app/data/kg_nodes.csv`。

CSV 共 **15,135 行症状节点**，全部 node_type 为 symptom，ID 与名称无重复。原 CSV 不修改、不裁剪，不再将应用的词表限制为 10 个 DEMO 节点。默认保留原始 P 编号，例如 Fever=P835、Cough=P4018、Headache=P885。

此文件包含症状/表型名称以及部分上位概念、家族史或本体元信息，例如 All、Mode of inheritance。既然此次要求覆盖整个文件，系统全部加载，不自行删除这些行。因此“随机追问可抽到某节点”不代表该节点适合真实问诊；真实问题策略应由队友的 Informed Search 模块负责。

## 2. 全词表与随机候选模块

默认设置改为：

- `KG_NODE_FILE`：项目内 kg_nodes.csv。
- `REASONING_MODE=random`：独立集成测试模式。
- `RANDOM_SEED=20260915`：相同种子、相同输入得到可复现抽样。
- `SESSION_DB` 默认 sessions-fullkg.sqlite3：与旧 DEMO 会话隔离，旧数据库不删除。

`RandomRecallService` 从 50 个标记为 SIM 的合成疾病条目中抽取 3–6 个候选，分数也是随机排序值。CSV 本身没有疾病节点，不能把这些模拟条目声称为从该 CSV 提取的真实疾病。候选的 source 明确为 seeded-random-fixture-v1，界面也标记为 Integration fixtures only。

`RandomSearchService` 从完整症状池中抽一个下一步追问，排除当前已肯定/否定的症状，以及已问过、已回答不确定而应跳过的症状。固定随机种子用于复现测试，不是医学搜索策略。达到已有轮数上限仍正常停止，随机模式不会靠虚假的疾病收敛伪造诊断结论。

原来的确定性 `mock` 模式保留，用于复跑旧 DEMO 回归。真实系统继续使用 `remote` 模式，调用既有 HTTP 适配器；随机实现不会在 remote 出错时偷偷接管。

扩展到 15,135 个概念后，还调整了两个实现细节：概念别名反向索引只遍历一次，避免逐节点扫描全部别名；RRF 使用排名得分字典，避免对每个候选反复在线性列表查找位置。全量概念均进入本地 MiniLM 检索索引，不只是出现在前端列表中。

## 3. 修复一：自由描述时回答选项不消失

原来的显示条件只有“会话正在等待问题”，没有区分用户选择哪种回答方式。因此，即使开始输入自由描述，Yes / No / Not sure 仍一直显示。

现在增加按当前问题维护的回答模式：

1. 点击 **Describe in my own words**，立即隐藏三个选项。
2. 直接聚焦输入框也自动进入自由描述模式。
3. 可点击 **Show answer choices** 切回，不会丢失已经输入的文字。
4. 请求处理中不显示可点击的回答选项。
5. 如果自由文本只补充了另一个症状、旧问题仍未回答，旧问题继续保持自由描述模式。
6. 如果后端真正给出一个新的追问，回答模式才为新问题重置；界面明确显示 Answering: 症状名称。因此新问题的选项出现不等于旧弹框没有关闭。

改动：frontend/src/stores/chat.ts、components/ChatInput.vue、views/ChatView.vue、styles.css。

## 4. 修复二：知识按钮一直解释起始症状

原按钮实际上发送固定字符串 `What is a fever?`，与后续描述完全无关。本次移除硬编码，按钮改为请求解释最新记录的症状，由后端维护主题，前端显示当前 Knowledge topic。

新增持久化字段 `knowledge_focus`，它与 `next_symptom` 分开：

- 自由描述成功合并 B：知识主题更新为 B。
- 又描述 C：主题更新为 C。
- 再次提到原本已经存在的 B：按最新事件更新为 B，不按证据数组中最初插入的位置选择。
- 点击 Yes / No / Not sure 回答追问，或手动纠正证据：主题更新为实际被回答/纠正的症状。
- 知识问答只增加消息版本，不修改症状证据、不消耗追问 round、不清掉 pending question。
- 刷新恢复会话时恢复同一个知识主题。
- 输入一个未识别的新描述后，将主题清空；再点知识按钮会要求明确症状，不沿用起始症状。
- 明确输入 `What is Fever?` 时，当前这次回答按明确名称解释，即使最新记录的症状是 Headache；这不会篡改证据。

来源也按目标概念约束：不能只因语义相近，就拿 A 的文档回答 B。对于 Fever/Cough 等已有匹配说明的主题，走对应来源的检索增强回答。对于仅有 CSV 名称、没有定义的节点，展示该节点名称、ID 和目录来源，并明确“没有医学定义/已验证解释资料”。全量目录可覆盖主题定位，但不是新增了 15,135 篇医学知识文章，也不让小模型凭记忆补造定义。

改动：chat_models.py、chatbot_service.py、dialogue_ai.py、前端状态和知识按钮。

## 5. 全量测试设计

### 5.1 每个症状都测试，不靠随机碰到

`scripts/evaluate_full_kg.py --check` 对全部 15,135 个节点生成五种输入：

| 类型 | 模板 | 期望 |
| --- | --- | --- |
| 阳性 | I have {名称}. | 原始 ID，present |
| 阴性 | I do not have {名称}. | 原始 ID，absent |
| 不确定 | I am not sure whether I have {名称}. | 原始 ID，uncertain |
| 家庭主体 | My father has {名称}. | 不进入本人证据，进入排除项 |
| 历史语境 | I used to have {名称} last year. | 不进入当前证据，进入排除项 |

总计 **75,675 条**。逐条结果写入 evaluation/full_kg_cases.jsonl，节点级覆盖、失败与数据 SHA-256 写入 full_kg_report.json。

另外，每个节点都作为唯一未排除的候选验证随机追问可达性，并验证其知识主题能定位回相同 ID。还用 30 个种子检查候选抽样与排除行为。这样覆盖了每个节点，而非寄希望于一次随机测试碰到所有节点。

首次发现 18 条失败，原因是 6 个节点名称自己含有 History of 等文字，被旧时间规则误排除。修复为只在匹配实体周围寻找断言/时间线索，实体名称内部不当作语境；普通 `history of Fever` 仍按历史语境处理。初次结果保留 full_kg_report_initial.json。

这些是规范名称模板和接口覆盖测试，**不证明每个症状的所有英语转述、医学语义或 LLM 都完全正确**。

### 5.2 真实 LLM 与全量覆盖分开记录

全量本地模型索引加载了全部节点。`evaluate_full_kg_llm.py` 通过实际 HTTP 请求调用真实 Qwen + MiniLM，默认固定随机抽取 20 个 CSV 节点，轮换阳性/阴性/不确定输入，报告保存模型调用和回退。

首轮 19/20：Limited knee flexion 被额外扩展成另一个相近概念。新增约束：模型提出的概念如果覆盖了已经被规则准确链接的规范实体区间，且 ID 不同，就拒绝该扩展，避免一个明确名称被算成两个症状。复测仍暴露出模型把纯断言短语 not sure 当成另一症状的来源，因此进一步禁止用这类短语为额外症状提供证据。两次失败报告分别保留 full_kg_llm_report_initial.json 与 full_kg_llm_report_overlap_guard.json；最终数字以 full_kg_llm_report.json 为准。由于用失败样例修复过实现，这是开发回归，不是独立测试集。

需要每个节点都通过真实 LLM/API 执行时使用 `--count 0`，脚本逐条保存进度。它会调用 15,135 次模型和会话编排，可能需要数小时；本次全节点覆盖采用上面的确定性测试，真实模型实测是单独标明的固定随机抽样，不混称全量 LLM 验证。

### 5.3 浏览器与回归

新增 frontend/browser-fullkg.cjs：真实 Chrome、真实 Qwen、本地全词表，重现自由描述切换与 Fever→Cough→Headache→Cough 的主题变化；检查刷新、知识问答状态保持、全词表搜索、移动端和 JavaScript 错误。

| 责任 | 保留入口 | 协议 |

## 8. 复现两个修复的人工步骤

1. 输入 `I have Fever.`，出现随机追问。
2. 点击 Describe in my own words，确认三个选项消失；也可 Show answer choices 切回。
3. 输入 `I have Cough.`，点击 Ask a knowledge question，主题必须是 Cough。
4. 输入 `I have Headache.` 后再点，主题必须是 Headache，并说明当前缺少其定义，不能解释 Fever。
5. 刷新再点，主题仍为 Headache；重新输入 Cough 后，主题应回到 Cough。
6. 每次知识问答前后检查证据、追问名称和 Follow-ups 轮数保持不变。

这是此次修改的文字记录与验证入口；实测数量和失败以配套 JSON 报告为准。
